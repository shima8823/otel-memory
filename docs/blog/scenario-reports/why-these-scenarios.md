# シナリオ選定の設計思想

このドキュメントは、`docs/blog/paper-structure.md` の
「なぜ複数シナリオが必要か（原因の切り分け）」を具体化するための設計メモです。

本記事では、シナリオを単なる再現ネタとしてではなく、
実務で使える診断力を育てる教材として選定します。

## 1. なぜ複数シナリオが必要か

同じ「メモリ高騰」でも、原因は複数あります。

- 入力過多で処理が追いつかない
- 保持待ちが長くバッファが増える
- 属性の組み合わせ増加で状態が膨張する

見た目が似たメトリクスでも、主因が違えば対処は変わります。
この切り分けを学ぶために、複数シナリオを扱います。

## 2. シナリオ選定に使う7つの視点

### 2.1 再現性

誰が実行しても、同じ傾向の症状が出るかを重視します。
必要な設定ファイル、コマンド、負荷条件を固定し、手順を短く保てるシナリオを採用します。

### 2.2 観測可能性

症状だけでなく、原因構造まで追えることを重視します。
`otelcol_*` メトリクスで異常を捉え、pprof で「どの構造が膨らんだか」を説明できるものを選びます。

### 2.3 単因子性

主原因を1つに寄せて説明できることを重視します。
複合要因が強すぎるケースは、導入教材ではなく応用編で扱います。

### 2.4 調整可能性

パラメータ変更で改善を確認できることを重視します。
「何を変えると、どのメトリクスがどう変わるか」を示しやすいシナリオを優先します。

### 2.5 実務頻度

現場で実際に起きやすい事故を優先します。
再現が面白いだけで、実務でほぼ起きないケースは優先度を下げます。

### 2.6 教育的価値

1つのシナリオの学びが、別コンポーネントに転用できるかを重視します。
個別知識ではなく、原因分類の型を学べるものを採用します。

### 2.7 コスト対効果

準備コストと説明コストに対して、得られる理解が大きいかを重視します。
短い手順で深い洞察を得られるシナリオを優先します。

## 3. 原因分類の基本方針

本記事では、原因を「症状とデータ構造」から分類します。

- キュー滞留型: 送信待ちの増加によりメモリが上がる
- 状態膨張型: ステートフル処理で内部状態が増え続ける
- 保持遅延型: 判定待ちやバッチ待ちでデータ保持が長引く

7つの視点は、この分類を教材として成立させるための観点です。

## 4. 本記事で扱う代表シナリオ

本記事では、以下の3つのシナリオを代表として取り上げる。

| シナリオ | 原因の軸 | 原因分類 | 主因コンポーネント | 再現コマンド |
|---------|---------|---------|------------------|------------|
| Tail Sampling | 時間軸 | 保持遅延型 | `tail_sampling` processor | `make scenario-tail-sampling` |
| 高カーディナリティ | 空間軸 | 状態膨張型 | `spanmetrics` connector | `make scenario-spanmetrics` |
| Batch × Queue メモリ増幅 | 流量軸 | キュー滞留型 | `batch` processor + `sending_queue` | `make scenario-batch-queue` |

### Tail Sampling（時間軸: 保持遅延型）

**選定理由**: `tail_sampling` processor は `decision_wait` の間、全トレースをメモリに保持する。
待機時間と流量の積がメモリ消費量を決めるため、パラメータ1つの変更で症状が大きく変わる。
これは「調整可能性」と「単因子性」の点で教材として優れている。

#### なぜ Tail Sampling が特別か — Batch Processor との比較

一見すると、Tail Sampling の `decision_wait` は Batch Processor の `timeout` と似ている。
`num_traces` も `send_batch_size` と同じバッファサイズに見える。
しかし、両者には根本的な違いがある。

| | Batch Processor | Tail Sampling |
|---|---|---|
| 待機の目的 | 効率的な一括送信 | トレース全体の到着を待って判定 |
| 保持時間 | `timeout`: 200ms（デフォルト） | `decision_wait`: 10-30s（典型値） |
| 解放トリガー | サイズ到達 **または** タイムアウト（早い方） | `decision_wait` 経過後に判定完了 ※1 |
| 保持対象 | 個別スパン（相関なし） | 同一トレースID の全スパン（相関あり） |
| メモリ概算 | `timeout × 流量 × サイズ` | `decision_wait × 流量 × サイズ` |
| 概算例（1,000 spans/sec, 1KB/span） | 0.2s × 1,000 × 1KB ≈ **0.2 MB** | 30s × 1,000 × 1KB ≈ **30 MB** |

※1: `num_traces` 超過時は古いトレースが早期 drop される場合もある。

Batch はスパンを**独立に**バッファし、200ms 以内に送信して解放する。
Tail Sampling は**トレース単位で判定する**ため、同一トレースの全スパンが `decision_wait` の間ずっと保持される。

保持時間が 150 倍違うため、同じスループットでもメモリ影響が桁違いになる。
Batch の `timeout` 変更が単体でメモリ問題になることは稀だが（高流量環境では例外あり）、
Tail Sampling の `decision_wait` を安易に大きくすると即座にメモリ高騰を招く。
この「パラメータ1つで劇的に変わる」特性が、教材としての扱いやすさにつながっている。

**学びの要点**: 時間軸のバッファリングがメモリに与える影響を理解し、
`decision_wait` と `num_traces` の適切な見積もり方法を身につける。
Batch との違いを知ることで、「同じタイムアウトでもコンポーネントの設計意図によってメモリ影響が異なる」という原則を学ぶ。

### 高カーディナリティ（空間軸: 状態膨張型）

**選定理由**: ステートフル processor/connector が高カーディナリティ属性を処理すると、
内部マップが無限に膨張する。開発環境では問題なく、本番で突然発生する点で「実務頻度」が高い。
GC後もメモリが戻らないという特徴的なシグネチャで、診断の型を学べる「教育的価値」がある。

**学びの要点**: 属性のカーディナリティが内部データ構造に与える影響を理解し、
ステートフルコンポーネント導入時のチェック手順を身につける。

### Batch × Queue メモリ増幅（流量軸: キュー滞留型）

**選定理由**: `batch` processor の `send_batch_size` と `sending_queue` の `queue_size` の掛け算が、
理論上のメモリ消費量を決定する。デフォルト値（`send_batch_size: 8192` × `queue_size: 5000`）では
最大約4,100万スパン ≈ 20GB のメモリ消費ポテンシャルがあり、
開発環境の低トラフィックでは顕在化せず本番の traffic spike で初めて OOM に至るパターンが多い。

```
メモリ消費（理論最大値）≈ send_batch_size × queue_size × avg_span_size
                        = 8192 × 5000 × 500B
                        ≈ 20GB
```

パラメータ2つの変更（`send_batch_size` 縮小 + `queue_size` 適正化）で改善を示せるため、
「調整可能性」が高い。また、デフォルト値の危険性という実務的な教訓を含む点で「実務頻度」も高い。

**Batch Processor の今後について**: OTel コミュニティでは exporter-level batching（`sending_queue.batch`）
への移行が推進されている（[opentelemetry-collector#13766](https://github.com/open-telemetry/opentelemetry-collector/issues/13766)）。
将来的に batch processor は非推奨になる可能性がある。
ただし、本記事執筆時点（2026年2月）では batch processor は広く使われており、
本シナリオの本質的な教訓 — **バッファの掛け算がメモリを支配する** — は
exporter-level batching でも `queue_size` チューニングとして引き続き有効である。

**学びの要点**: パイプライン上の複数バッファの掛け算効果を理解し、
`send_batch_size`、`queue_size`、`num_consumers` の適切な見積もり方法を身につける。

### 補足: 3シナリオの鑑別

3つのシナリオは異なる Heap パターンを示し、原因の鑑別に使える。

| シナリオ | Heap パターン | 鑑別ポイント |
|---------|-------------|------------|
| Tail Sampling | 急騰→高止まり→解放 | 負荷停止後にメモリが回復する |
| 高カーディナリティ | 右肩上がり（GC後も戻らない） | 負荷停止後もメモリが戻らない |
| Batch × Queue | 階段状に増加→queue排出で急降下 | exporter queue メトリクスと連動する |


## 5. 各シナリオを説明するときの共通フォーマット

各シナリオ本文は、次の順で記述します。

1. 再現手順（再現性）
2. 観測ポイント（観測可能性）
3. 主因の特定（単因子性）
4. パラメータ調整と再観測（調整可能性）
5. 実務での発生パターンと監視（実務頻度）
6. 他シナリオへの転用（教育的価値）
7. 最小手順での学びの要約（コスト対効果）
